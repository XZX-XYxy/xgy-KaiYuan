# ThingsBoard 设备遥测与检修协同

## AI 增强版设计方案与流程图 2

版本：V1.0

日期：2026-10-29

依据：现场调研报告、行业痛点分析、GitHub 类似方案调研、无 AI 系统流程图。

设计定位：在原有“遥测采集、规则告警、工单检修、恢复核验”闭环上增加只读 AI 辅助层，帮助人员识别重复告警、发现被淹没的新事件、解释归并依据，并从维修手册、历史工单和备件资料中整理检修建议。AI 不执行设备控制，不替代人工确认，不自动关闭告警或修改工单。

## 1. 设计结论

### 1.1 核心问题

现场调研中的典型问题是：同一设备出现五条相似温度告警，维修员将其理解为重复重传，但其中一条振动异常实际是新事件。问题的根因不是告警条数，而是以下四类信息没有对齐：

1. 时间轴未对齐：发生时间、补传时间、采集时间和平台接收时间混用。
2. 设备身份未对齐：现场外号、铭牌号、ThingsBoard 设备 ID 和工单资产号缺少稳定映射。
3. 事件身份未对齐：相同事件 ID、缺失事件 ID 和不同事件 ID 的告警被混在一起处理。
4. 责任与动作未对齐：谁可以归并、谁可以回退、谁可以关闭告警、谁可以确认恢复产出没有明确。

因此，AI 的切入点不是“预测所有故障”，而是“帮助人员看清证据和候选关系”。

### 1.2 AI 增强版应解决的问题

| 设计目标 | AI 的作用 | 必须保留的人工控制 |
| --- | --- | --- |
| 减少重复告警干扰 | 对候选告警组给出相似原因、差异点和证据 | 人工确认归并、拒绝归并或回退 |
| 防止新故障被淹没 | 标出组内可能的新事件、独立测点和异常变化 | 现场维修员核实设备状态 |
| 解释系统结论 | 引用原始遥测、事件 ID、时间字段和手册片段 | 授权人员核对引用是否充分 |
| 加快检修准备 | 汇总历史工单、手册版本、备件和未结事项 | 检修计划员确认可用性和停机窗口 |
| 降低误操作风险 | 对低置信、缺证据和越权请求进行阻断 | 上锁挂牌、停机、复产和工单变更仍由人执行 |

### 1.3 设计边界

AI 可以做：

- 告警重复候选分组。
- 疑似新事件提示。
- 归并原因与差异解释。
- 原始遥测、时间字段和事件 ID 的引用。
- 维修手册、历史工单和备件资料检索。
- 检修建议草稿、风险摘要和待核实问题清单。
- 人工纠正后的记录归档和评测样本生成。

AI 不可以做：

- 直接关闭或确认 ThingsBoard 告警。
- 直接创建、分派、完成或关闭真实工单。
- 自动停机、启动、复位、解锁或控制设备。
- 代替上锁挂牌、作业许可和安全审批。
- 自动排产、承诺交期或确认恢复产出。
- 对传感器漂移直接下故障结论。
- 删除缺少事件 ID 的异常记录。
- 读取用户负责资产组之外的遥测。

## 2. 调研约束到设计规则的转换

| 调研事实 | 设计规则 |
| --- | --- |
| 五条温度告警为重复候选，但振动异常是新事件 | 归并只产生候选组，原始事件逐条保留；新事件必须有独立标记和人工核实入口 |
| 断联本地记录回传后，补传时间不能当作发生时间 | 数据模型同时保存 occurrence_time、ingest_time、source_cycle 和时区偏移 |
| 传感器漂移时读数变高，不能直接认定轴承损坏 | AI 输出“数据质量待查”或“现场核实建议”，不得输出确定性故障结论 |
| 技师使用设备外号，系统使用铭牌号 | 建立 alias、nameplate_id、canonical_asset_id 和 asset_group 的受控映射 |
| 去重按设备和事件 ID，缺 ID 保留候选 | 缺事件 ID 的记录进入待核队列，不自动合并、不自动删除 |
| 工单需要设备、异常事件、手册版本和可用备件 | 工单资料包必须引用异常事件、手册版本、备件状态、上次检修和未结事项 |
| 模型建议不能替代上锁挂牌和授权检修 | AI 输出与设备控制权限物理隔离；控制类请求硬阻断 |
| 用户只能查看负责设备 | AI 上下文构建前执行资产组授权检查，越权数据不进入模型 |
| 维修完成与恢复产出不是同一件事 | 分别建立维修完成时间和恢复产出确认时间，分别由人签字 |
| 试点只针对两类模拟设备，保留原告警和人工流程 | 第一阶段只读影子运行，不接写接口，可与原流程并行对照 |

## 3. 用户与权限设计

| 角色 | 主要职责 | 关键权限 | 当前待确认项 |
| --- | --- | --- | --- |
| 设备运维经理 | 业务目标、验收和风险接受 | 查看汇总、批准试点、接受验收 | 预算、最终验收签字权 |
| 现场维修员 | 现场核实、维修执行、漂移或新事件判断 | 查看本人资产组、提交现场核实意见 | 是否拥有归并回退权 |
| 检修计划员 | 工单资料、手册版本、备件、停机窗口 | 维护检修资料包、核对待办 | 工单状态变更权限 |
| 物联网工程师 | 设备标识、时间口径、数据质量和接口 | 维护映射、查看技术审计 | 映射表最终维护责任人 |
| 作业安全员 | 控制边界、作业许可和安全红线 | 设置禁止动作、审核越权事件 | 停止边界和解除责任人 |
| 生产值班长 | 恢复产出和排产确认 | 确认恢复产出、提出排产建议 | 恢复签字责任划分 |
| AI 辅助服务 | 只读分析和建议生成 | 仅访问授权上下文，不拥有业务写权限 | 模型供应商和部署方式 |

权限原则：

1. 最小权限：AI 服务只拥有读取授权上下文的权限，不拥有 CMMS 和 ThingsBoard 写权限。
2. 资产组隔离：在检索遥测、工单、手册和备件之前先执行资产组校验。
3. 人机分离：AI 建议、人工决策、业务写入、设备控制分别由不同服务和权限域承担。
4. 全量留痕：查看、提示、接受、拒绝、回退和修改都记录操作者、时间和原因。

## 4. 总体系统设计

### 4.1 逻辑架构

系统分为六层：

1. 现场层：传感器、PLC、边缘网关，负责采集和本地缓存。
2. 物联网平台层：ThingsBoard 负责设备接入、遥测、规则链、告警和看板。
3. 数据治理层：负责时间校准、设备身份解析、资产组校验、原始事件保留和候选事件分组。
4. AI 辅助层：负责证据组装、候选关系判断、解释生成和资料检索。
5. 人工协同层：负责人工评审、现场核实、归并确认、回退、工单资料准备和恢复确认。
6. 业务审计层：负责工单关联、维修记录、恢复产出记录、审计日志和评测反馈。

建议组件如下：

| 组件 | 职责 |
| --- | --- |
| ThingsBoard Adapter | 读取设备、遥测和告警，不直接写回告警 |
| Identity & Time Service | 解析外号、铭牌号、规范资产号、时区、发生时间和补传时间 |
| Event Governance Service | 按设备和事件 ID 建立候选组，保留原记录，支持回退 |
| Asset Access Guard | 在 AI 调用前校验用户和资产组，拒绝越权数据 |
| Context Builder | 组装原始遥测、手册版本、历史工单、备件和未结事项 |
| AI Assist Service | 生成候选关系、差异解释、风险摘要和检修资料草稿 |
| Output Validator | 校验证据引用、资产组、时间字段、置信度和禁止动作 |
| Human Review Console | 展示原遥测、候选组、AI 理由、引用和人工操作入口 |
| CMMS Connector | 第一阶段只读或人工代理，后续经审批开放受控写入 |
| Audit & Feedback Store | 保存 AI 版本、提示词版本、输入快照、输出、人工决定和纠正样本 |

### 4.2 数据流

```text
传感器 / PLC / 边缘网关
        ↓
ThingsBoard 遥测、规则链、告警
        ↓
身份与时间校准 → 资产组授权 → 原始事件保全
        ↓
按设备 + 事件 ID 建立候选组
        ↓
上下文构建 → AI 只读分析 → 输出校验
        ↓
人工评审与现场核实
        ↓
人工确认归并 / 回退 / 新事件 / 数据质量待查
        ↓
工单资料包 → 维修完成
        ↓
独立恢复产出确认
        ↓
关闭、保持打开或升级
        ↓
审计、指标统计和评测样本
```

### 4.3 三个不可跨越的闸门

1. 数据闸门：设备、时间、资产组和原始事件未通过校验时，不进入 AI。
2. AI 输出闸门：证据不足、引用缺失、越权、低置信或出现控制意图时，输出不得进入建议队列。
3. 业务动作闸门：任何告警关闭、工单状态变更、停机和复产动作都必须由授权人员通过独立系统执行。

## 5. 核心模块设计

### 5.1 时间与设备身份模型

遥测和告警事件应至少包含以下字段：

| 字段 | 说明 |
| --- | --- |
| occurrence_time | 现场真实发生时间，用于事件排序和去重 |
| ingest_time | 平台接收或补传时间，仅用于数据质量分析 |
| source_time | 边缘设备记录的原始时间 |
| source_cycle | 原始采集周期或 NASA cycle 等来源字段，单独解释 |
| timezone_offset | 设备侧或平台侧时区偏移，需明确基准 |
| device_alias | 现场外号 |
| nameplate_id | 设备铭牌号 |
| canonical_asset_id | 唯一规范资产号 |
| asset_group_id | 用户可访问的资产组 |
| event_id | 原始事件 ID |
| source_event_id | 外部系统事件 ID |

设计规则：

- occurrence_time 与 ingest_time 必须同时保存，禁止覆盖。
- 断联补传记录打上 `BACKFILLED` 标记，并显示本地记录时间和回传时间。
- 设备别名只用于检索，不直接作为业务主键。
- 映射冲突进入待核队列，不自动选择其中一个设备。
- 缺少事件 ID 的事件进入 `MISSING_EVENT_ID` 队列。

### 5.2 原始事件保全与可回退归并

归并不能破坏原始记录。每条原始告警、遥测片段、来源时间和事件 ID 必须保留在事件仓中。

候选组字段建议：

| 字段 | 说明 |
| --- | --- |
| candidate_group_id | 候选组唯一标识 |
| canonical_asset_id | 规范资产号 |
| event_ids | 组内引用的事件 ID |
| first_occurrence_time | 组内最早发生时间 |
| last_occurrence_time | 组内最晚发生时间 |
| first_ingest_time | 组内最早接收时间 |
| last_ingest_time | 组内最晚接收时间 |
| group_reason | 规则、AI 或人工给出的分组原因 |
| source_refs | 原始遥测、告警和资料引用 |
| status | PROPOSED、HUMAN_VERIFIED、REJECTED、ROLLED_BACK |
| reversible | 是否可回退 |

操作要求：

1. 归并操作只能作用于候选组，不能覆盖原始事件。
2. 归并前展示首末发生时间、首末接收时间和全部原始事件。
3. 人工可以拒绝归并、拆分候选组或回退到原始记录。
4. 回退后保留原候选组、回退原因和操作者，不删除历史。
5. 任何缺少事件 ID 的事件不可自动进入已确认组。

### 5.3 AI 辅助服务

AI 辅助服务采用“规则优先、AI 补充”的设计，不把模型作为唯一判断者。

处理流程：

1. 输入校验：检查资产组、时间字段、原始事件引用和用户权限。
2. 上下文构建：提取候选组前后时间窗口的原始遥测、规则事件、设备映射、手册版本、历史工单、备件和未结事项。
3. 候选分析：识别可能重复、可能新事件、数据质量可疑和时间口径冲突。
4. 证据生成：每条结论必须引用原始遥测点、事件 ID、规则命中、手册片段或历史工单。
5. 输出校验：检查是否出现越权、无证据、控制指令、停机建议或确定性故障结论。
6. 人工队列：验证通过的输出进入待评审队列，不直接写回业务系统。

AI 输出示例：

```json
{
  "task": "alarm_group_review",
  "asset_id": "ASSET-001",
  "candidate_group_id": "CG-20261029-018",
  "possible_duplicate_count": 5,
  "possible_new_event": true,
  "new_event_candidates": [
    {
      "event_id": "EVT-VIB-021",
      "reason": "振动测点变化与温度重传时间不一致",
      "evidence_refs": [
        "telemetry:EVT-VIB-021",
        "alarm:EVT-TEMP-001",
        "alarm:EVT-TEMP-005"
      ]
    }
  ],
  "data_quality_warnings": [
    "温度读数可能受传感器漂移影响，不能据此认定轴承损坏"
  ],
  "confidence": 0.72,
  "uncertainties": [
    "缺少现场核实记录",
    "部分事件缺少 source_event_id"
  ],
  "recommended_human_checks": [
    "现场核对振动测点",
    "确认温度传感器是否校准",

  ],

```

输出中不得出现直接执行字段，例如 `execute=true`、`auto_close=true` 或设备控制命令。

### 5.4 人工评审与回退

人工评审界面应同时展示：

1. 原始告警列表及每条告警的事件 ID。
2. occurrence_time、ingest_time、source_time 和时区偏移。
3. 设备外号、铭牌号和规范资产号。
4. 原始遥测曲线及候选组前后时间窗口。
5. AI 给出的重复候选、新事件提示、差异理由和引用。
6. 手册版本、历史工单、备件和未结事项。
7. 当前资产组和操作者权限。

人工可执行的动作：

- 接受为重复候选组。
- 拒绝归并。
- 将某条事件拆分为新事件。
- 标记传感器漂移或数据质量待查。
- 回退到原始记录。
- 升级给设备运维经理或安全员。

所有动作必须填写原因。回退操作必须生成新的审计记录，不能覆盖原记录。

### 5.5 工单、维修完成与恢复产出

工单资料包至少关联：

- 设备规范资产号。
- 异常事件和候选组。
- 维修手册版本。
- 可用备件和库存状态。
- 上次检修记录。
- 未结事项。
- 可申请停机窗口。
- AI 建议及人工核实结论。

维修完成与恢复产出分开记录：

| 判定 | 记录人 | 记录内容 | 当前状态 |
| --- | --- | --- | --- |
| 维修完成 | 维修员与检修计划员，具体签字责任待确认 | 维修措施、更换备件、工时、遗留事项 | 规则可设计，签字责任待定 |
| 恢复产出 | 生产值班长与安全员，具体签字责任待确认 | 连续健康数据、现场确认、复产条件 | 规则可设计，签字责任待定 |

AI 可以整理证据和生成摘要，但不能签署维修完成或恢复产出。

### 5.6 审计与反馈

每次 AI 调用必须保存：

- 用户与资产组。
- 输入上下文快照和引用范围。
- 模型名称、版本、提示词版本和运行参数。
- AI 原始输出和校验结果。
- 人工接受、拒绝、修改或回退的理由。
- 后续工单、维修和恢复记录。
- 是否发生越权、控制意图或证据缺失。

人工纠正结果进入离线评测集，用于改进提示词、检索和规则。第一版不进行在线自动学习和自动更新模型。

## 6. 流程图 2：有 AI 后的系统流程

### 6.1 流程说明

流程图 2 在无 AI 流程的基础上增加四个 AI 相关环节：

1. 上下文构建：只提取授权资产组内的原始遥测和业务资料。
2. AI 分析：给出重复候选、新事件候选、证据和不确定性。
3. 输出校验：阻断无证据、越权、低置信和控制类输出。
4. 人工评审：由人决定接受、拒绝、拆分、回退或升级。

AI 不进入设备控制链路，也不直接进入 CMMS 写链路。

### 6.2 异常分支

| 异常 | 系统处理 | 人工处理 |
| --- | --- | --- |
| 缺少事件 ID | 标记 MISSING_EVENT_ID，保留原事件 | 秦序或指定复核人核对 |
| 断联补传 | 保留 occurrence_time 和 ingest_time，标记 BACKFILLED | 维修员核对本地记录 |
| 设备别名冲突 | 进入映射冲突队列，不自动选择 | 物联网工程师与维修员确认 |
| 传感器漂移 | 标记数据质量可疑，不下故障结论 | 现场校准和核实 |
| AI 置信度低 | 输出进入低置信候选队列 | 维修员或运维经理判断 |
| AI 引用缺失 | 输出校验失败，不进入建议队列 | 技术人员排查上下文 |
| AI 服务不可用 | 自动降级到无 AI 流程 | 保持原人工流程 |
| 资产组越权 | 拒绝读取和推理，记录审计 | 安全员核查权限 |
| 出现控制意图 | 硬阻断，不执行任何设备动作 | 按授权和安全流程处理 |
| 新事件被误并 | 支持拆分和回退到原始记录 | 维修员确认并修正 |
| 维修完成但未恢复 | 保持告警或风险打开，升级处理 | 生产值班长确认恢复产出 |

### 6.3 状态机

事件状态：

RAW -> NORMALIZED -> CANDIDATE_GROUP -> AI_REVIEWED -> HUMAN_VERIFIED -> ACTION_RECORDED -> AUDITED

AI 建议状态：

GENERATED -> VALIDATED -> PENDING_HUMAN -> ACCEPTED / REJECTED / ROLLED_BACK

工单状态：

DRAFT -> OPEN -> ASSIGNED -> IN_PROGRESS -> REPAIR_COMPLETED -> RECOVERY_PENDING -> RECOVERED / ESCALATED -> CLOSED

其中 REPAIR_COMPLETED 与 RECOVERED 必须分离，不能用同一个字段表示。

## 7. 验收设计

### 7.1 场景验收

使用调研报告中的合成样本：

- 一班次 120 条事件。
- 18 条重复候选。
- 5 条相似温度告警。
- 1 条独立振动异常。
- 断联补传样本。
- 传感器漂移样本。
- 缺少事件 ID 样本。
- 资产组越权样本。
- AI 控制意图样本。

验收底线：

1. 关键异常不得被归并丢失。
2. 新振动事件必须能被单独识别并进入人工核实。
3. 每一条归并结果都能回退到原始记录。
4. 首末发生时间和首末接收时间均被保留。
5. 补传时间不能替代发生时间参与排序。
6. 缺事件 ID 的记录必须进入待核队列。
7. AI 的每条结论必须有可追溯引用。
8. AI 不能执行任何业务写操作或设备控制。
9. 资产组之外的遥测必须拒绝。
10. AI 服务故障时，原有人工流程仍然可用。

### 7.2 指标

| 指标 | 目标 |
| --- | --- |
| 原始事件保留率 | 100% |
| 归并结果可回退率 | 100% |
| 关键异常丢失数 | 0 |
| AI 结论引用可追溯率 | 100% |
| 越权遥测访问数 | 0 |
| AI 触发的设备控制动作数 | 0 |
| 缺 ID 事件自动删除数 | 0 |
| 人工纠正留痕率 | 100% |

告警数量下降不能单独作为成功指标。应同时统计人工复核时间、重复候选确认率、误归并率、新事件识别率、回退成功率和人工纠正率。

## 8. 实施阶段

### 阶段 0：口径准备

- 建立设备别名、铭牌号、规范资产号和资产组映射。
- 明确 occurrence_time、ingest_time、时区偏移和 source_cycle 口径。
- 明确归并、回退、告警关闭、工单状态和恢复产出的责任人。
- 只针对两类模拟设备准备样本。

### 阶段 1：只读影子运行

- 接入 ThingsBoard 只读数据。
- 保留原告警和人工流程。
- AI 只生成候选组、解释和待核实问题。
- 不开放 ThingsBoard 写接口。
- 不开放 CMMS 自动写接口。
- 不接设备控制接口。
- 用 120 条合成事件做逐条对照。

### 阶段 2：人工代理写入

仅在阶段 1 验收通过并且责任权限确认后考虑：

- 人工确认后生成工单草稿。
- 由授权人员点击提交。
- 所有写操作幂等并记录外部引用。
- 告警关闭和恢复产出仍保持独立审批。

### 阶段 3：扩大试点

- 增加设备类型。
- 增加资产组和角色。
- 建立模型评测集。
- 评估误归并、漏判和人工负担。

## 9. 停止条件

出现以下任一情况应暂停 AI 辅助功能，但保留原 ThingsBoard 告警和人工检修流程：

1. 关键异常被归并丢失。
2. 归并结果无法回退。
3. AI 结论无法给出原始证据引用。
4. AI 产生控制、停机、复产或工单自动变更请求。
5. 用户读取资产组之外的遥测。
6. 设备身份映射发生冲突且未处理。
7. 时间字段被错误覆盖，补传时间被当作发生时间。
8. 缺事件 ID 的记录被自动删除。

## 10. 尚待确认的问题

1. 归并错误后的回退由哪个岗位操作，留痕保存在哪个系统。
2. UTC 偏移以设备侧还是平台侧为准，NASA cycle 如何映射到业务时间。
3. 缺事件 ID 的候选由谁在多长时间内复核。
4. 设备别名与铭牌号对照表由谁维护，覆盖范围多大。
5. 谁有权确认告警关闭，谁有权修改工单状态。
6. 停止边界的解除权限属于安全员、值班长还是联合审批。
7. 恢复产出由维修员还是值班长签字，是否需要双人确认。
8. AI 建议的最低证据数量和置信度阈值。
9. 审计记录、遥测原文和 AI 输入快照的保留期限。
10. 两类模拟设备的结论能否外推到全车间。

## 11. 设计方案总结

该方案不是把 AI 放在告警前面自动做结论，而是把 AI 放在“证据整理和候选关系提示”位置：

1. ThingsBoard 继续作为遥测和告警事实来源。
2. 确定性服务负责时间、身份、权限和原始事件保全。
3. AI 只对经过授权的上下文做候选归并、新事件提示和资料摘要。
4. 人负责复核、归并、回退、工单和恢复产出。
5. 审计系统保存全部证据、建议和人工决定。

这样既能利用 AI 降低重复告警带来的认知负担，又不会把关键异常、设备控制和生产恢复交给模型。
