01 / 业务挖掘 02 / 10

真正的问题不是告警太多，
而是“看不出哪条是新事件”。

从合成一班次 120 条事件、18 条重复候选切入，保留现场故事作为整个系统的设计起点。

约 35 秒
“
五条温度告警看起来都一样，但其中一条振动异常其实是新事件。

维修员只能手工对时间轴、查设备编号、比对重传记录。告警减少不代表故障减少，关键异常必须被单独保留。

01时间口径发生时间、平台接收时间和补传时间混用。
02设备身份现场外号、铭牌号和系统设备 ID 没有统一映射。
03事件 ID重复上报与缺失 ID 无法可靠区分。
04责任闭环谁归并、谁核实、谁关单、谁确认恢复不清楚。
02 / 行业与竞品 03 / 10

遥测平台与 CMMS 都成熟，
真正稀缺的是中间协同层。

GitHub 上既有 ThingsBoard 遥测项目，也有成熟 CMMS，但“告警 → 人工核实 → 工单 → 恢复确认”的一体化实现很少。

约 35 秒

项目定位

ThingsBoard 是遥测与告警的事实来源；内部工单系统承载检修责任；AI 只负责证据整理。协同服务连接两侧。

  • 不重复建设 IoT 平台
  • 不把 AI 当成设备控制者
  • 不把告警减少当作唯一成功指标

代表项目节选

platform-integrationThingsBoard + CMMS 集成服务CMMS 闭环
Atlas CMMS工单、分派、维修与库存成熟 CMMS
ShuangAnIoT、工单、知识库与 Agent业务参考
结论：开发重点不是监控大屏，而是事件治理、工单闭环和恢复验证。
